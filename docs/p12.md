# P12 Development Order

P12 makes OpenNavier AI-native at the platform level. The goal is for agents to
help author new capabilities, tests, schemas, examples, and documentation while
humans and deterministic checks remain in control of what becomes executable.

Do not let AI-authored capabilities execute until they pass the same registry,
ontology, adapter, benchmark, plugin, and review gates as human-authored work.

## Community OS Position

P12 is not a shortcut around engineering validation. It is a supervised authoring
loop for growing the open-source simulation OS faster while keeping every new
capability reviewable, reproducible, and benchmark-backed.

## Development Order

### 1. AI Capability Authoring Workflow

Define the agent workflow for proposing a new capability.

Target behavior:

- Start from a user request, existing case, benchmark paper, or contributor
  proposal.
- Generate a draft capability manifest, ontology mapping, adapter needs,
  validators, benchmark plan, examples, docs, and test plan.
- Mark all generated material as draft until human review and tests pass.
- Refuse to generate hidden execution paths or raw solver files outside
  approved writer contracts.

Suggested implementation area:

- `packages/core/src/opennavier_core/capability_authoring.py`
- CLI or MCP proposal tools after package tests exist.

Acceptance signal:

- Tests use mocked model output to verify schema parsing, draft status,
  rejection of direct solver mutations, provenance, and required review gates.

### 2. Test And Benchmark Generation Assistance

Let agents help create evidence tasks before implementation.

Target behavior:

- Generate failing tests, benchmark manifests, analytical checks, fixture plans,
  and expected diagnostic behavior from a proposed capability.
- Require generated tests to be reviewed and run before production writers are
  implemented.
- Store test-generation provenance in the session or contribution artifact.

Suggested implementation area:

- Core authoring helpers.
- Test scaffolds in capability contribution tooling.

Acceptance signal:

- Tests cover generated test-plan validation, missing benchmark rejection,
  provenance, and refusal when expected behavior is underspecified.

### 3. Review And Promotion Loop

Use AI for review-style reasoning without letting it approve itself.

Target behavior:

- Agents can summarize diffs, compare implementation to manifests, inspect
  benchmark evidence, and propose review comments.
- Human review remains required before promotion to executable or certified.
- Failed review comments must be resolved and recorded.

Suggested implementation area:

- Core review artifact models.
- GitHub or local review tooling after core behavior exists.

Acceptance signal:

- Tests cover review artifact creation, unresolved comments, blocked promotion,
  resolved comments, and reviewer metadata.

### 4. Community Capability Catalog

Publish a local-first catalog of capabilities and trust states.

Target behavior:

- Show built-in, workspace, plugin, draft, experimental, verified, and certified
  capabilities.
- Expose support boundaries, required tools, benchmarks, examples, and known
  limitations.
- Keep catalog generation local and reproducible.

Suggested implementation area:

- Capability registry and plugin catalog tooling.
- Studio catalog view after package tests exist.

Acceptance signal:

- Tests cover catalog generation, filtering by trust state, missing evidence,
  plugin provenance, and stable output.

## P12 Completion Gate

P12 is complete only when:

- AI can draft capability artifacts only through typed schemas and draft states.
- Generated tests and benchmark plans come before behavior-bearing code.
- Human review and deterministic evidence are required for promotion.
- The capability catalog exposes support boundaries and trust states.
- Focused tests and the full available suite pass.
