# P3 Development Order

P3 adds advanced design automation and 3D workspace capabilities. These are
valuable only after the local simulation workflow is reproducible and the model
boundary is controlled.

Do not use P3 work to bypass P0 to P2 contracts. Geometry, mesh, simulation,
variant, and report artifacts must remain inspectable and reproducible.

## Desktop UI Position

P3 expands Studio from a workflow cockpit into an interactive design workspace.
This is where the Three.js editor belongs: sketching, selecting, manipulating
geometry, comparing variants, and viewing simulation result overlays.

The desktop UI can feel direct and visual, but it still must serialize every
meaningful edit into typed geometry operations, parameter changes, variant
manifests, or simulation artifacts. The Three.js scene is an editor and
inspection surface, not the durable source of truth.

## Development Order

### 1. Variant Manifest

Create a durable artifact for parametric design variants.

Target behavior:

- Store parent session, variant id, parameter values, bounds, generated files,
  commands, diagnostics, metrics, and ranking inputs.
- Keep variant artifacts local and path-safe.
- Make every variant reproducible from its manifest.

Suggested implementation area:

- `packages/core/src/opennavier_core/variants.py`
- Tests in `tests/test_variants.py`

Acceptance signal:

- Tests cover schema validation, parameter bounds, artifact references,
  deterministic JSON output, and workspace path safety.

### 2. Bounded Sweep Creation

Generate controlled parameter sweeps for supported case families.

Target behavior:

- Accept explicit parameters, bounds, and objective metrics.
- Generate a finite run queue.
- Refuse unbounded or ambiguous sweeps.
- Reuse deterministic templates and planner rules.
- Record generated variants in the session artifact.

Suggested implementation area:

- `packages/core/src/opennavier_core/sweeps.py`

Acceptance signal:

- Tests cover bounded sweep creation, invalid bounds, duplicate variants,
  deterministic ordering, and run queue generation.

### 3. Metric Extraction And Ranking

Compare variants using reproducible metrics before adding optimization.

Target behavior:

- Extract metrics from diagnostics, residual logs, reports, or explicit output
  files.
- Rank variants according to the objective.
- Mark failed or incomplete variants separately from valid candidates.
- Record limitations and next recommended iteration.

Suggested implementation area:

- `packages/core/src/opennavier_core/metrics.py`
- `packages/core/src/opennavier_core/ranking.py`

Acceptance signal:

- Tests cover metric extraction, missing metrics, failed variants, ranking
  behavior, tie handling, and deterministic recommendations.

### 4. Deterministic Parametric Design Loop

Run the first end-to-end local design loop without model guidance.

Target behavior:

- Generate variants.
- Initialize case directories.
- Run checks and solver commands through existing workflow contracts.
- Collect diagnostics and metrics.
- Produce a comparison report.
- Recommend the next bounded iteration from structured evidence.

Suggested implementation area:

- `packages/core/src/opennavier_core/design_loop.py`

Acceptance signal:

- Tests cover variant manifests, parameter bounds, run queue creation, metric
  extraction, ranking behavior, and report output.

### 5. Three.js Topology Workspace

Add the first interactive 3D design surface after backend geometry operation
contracts are explicit.

Target behavior:

- Provide a Three.js viewport for inspectable geometry and topology state.
- Serialize geometry operations as typed backend requests.
- Support selection state, undo, redo, and export handoff.
- Do not treat the frontend scene as the durable source of reproducibility.

Suggested implementation area:

- `apps/studio/src`
- Shared operation schema in core or a Studio backend bridge.

Acceptance signal:

- Frontend tests cover command serialization, selection state, topology
  operation payloads, undo/redo state, and export handoff to adapters.

### 6. Simulation Result Overlays

Add result visualization only after result artifact formats are stable.

Target behavior:

- Load structured result artifacts or generated visualization assets.
- Show contours, vectors, or variant comparisons in the 3D view.
- Keep units, time step, field name, source file, and provenance visible.
- Handle missing or incompatible result assets gracefully.

Suggested implementation area:

- `apps/studio/src`
- Result artifact schema in core if needed.

Acceptance signal:

- Frontend tests cover overlay payload loading, field selection, missing
  artifact handling, variant comparison state, and provenance display.

## P3 Completion Gate

P3 is complete only when:

- Variants are represented by reproducible local manifests.
- Bounded sweeps can generate deterministic run queues.
- Metrics and ranking are deterministic.
- The first no-model design loop can compare variants and recommend a bounded
  next step.
- Three.js topology operations are serialized through typed contracts.
- Result overlays consume stable artifacts rather than ad hoc files.
- Focused tests and the full available suite pass.
