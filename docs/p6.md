# P6 Development Order

P6 defines the multi-solver adapter SDK. The goal is to make OpenFOAM the
reference adapter while giving future solvers the same discovery, validation,
execution, diagnostics, results, and licensing contract.

Do not add first-class non-OpenFOAM workflows until the adapter SDK can prove
that solver integrations stay local, auditable, and capability-gated.

## Adapter Position

P6 turns solvers into replaceable local tools behind typed contracts. OpenNavier
does not become a solver and does not link against solver internals by default.
Adapters write inputs, run external commands, collect logs, parse outputs, and
return structured evidence.

## Development Order

### 1. Solver Adapter Contract

Define the `SolverAdapter` interface shared by solver packages.

Target behavior:

- Support discovery, version checks, capability declarations, input validation,
  input writing, execution command construction, log collection, diagnostics,
  result collection, and cleanup policy.
- Require adapters to expose licensing and runtime constraints.
- Use argument-list subprocess calls, never shell-string execution.
- Keep all writes inside approved workspace, case, or run directories.

Suggested implementation area:

- `packages/core/src/opennavier_core/adapters.py`
- Adapter implementations in solver-specific packages.

Acceptance signal:

- Tests cover fake adapter discovery, command construction, path safety,
  missing executables, nonzero exits, diagnostics output, and licensing fields.

### 2. OpenFOAM Reference Adapter

Refactor current OpenFOAM behavior to demonstrate the SDK contract.

Target behavior:

- Wrap existing OpenFOAM case-build, runner, log parsing, and diagnostics behind
  the adapter interface.
- Preserve existing CLI and MCP behavior.
- Keep OpenFOAM GPL boundary rules visible in adapter metadata.
- Avoid regressions in current cavity and duct workflows.

Suggested implementation area:

- Existing `packages/openfoam` modules.
- Compatibility tests around current CLI and MCP consumers.

Acceptance signal:

- Existing OpenFOAM tests pass, and new adapter-contract tests prove parity with
  current package APIs.

### 3. Adapter Packaging Template

Create a documented scaffold for future solver packages.

Target behavior:

- Provide a minimal adapter package layout, test fixtures, fake executable
  pattern, documentation template, and capability manifest example.
- Require integration tests to be marked and optional.
- Keep real solver installation outside default unit tests.

Suggested implementation area:

- `docs/adapter-sdk.md`
- Package template under a future templates or examples directory.

Acceptance signal:

- Documentation and tests show how to build an adapter without requiring a real
  solver installation.

### 4. First Non-CFD Adapter Plan

Prepare, but do not block on, first structural or thermal adapters.

Target behavior:

- Evaluate open-source candidates for linear FEA and thermal workflows.
- Record licensing, command-line behavior, input formats, output formats, and
  testability.
- Keep adapter selection separate from P6 completion.

Suggested implementation area:

- `docs/solver-adapter-candidates.md`
- Capability draft manifests after P4 exists.

Acceptance signal:

- Candidate notes identify viable first adapters and explain why any deferred
  solvers are not yet supported.

## P6 Completion Gate

P6 is complete only when:

- `SolverAdapter` is documented and contract-tested.
- OpenFOAM acts as the reference adapter without behavior regressions.
- Future adapters have a scaffold, fake-executable test pattern, and integration
  test boundary.
- Adapter metadata exposes licensing and runtime constraints.
- Focused tests and the full available suite pass.
