# P10 Development Order

P10 adds coupled workflow graphs and staged multiphysics orchestration. The goal
is to coordinate multiple tools and solvers without pretending that every
coupling is fully automated or validated.

Do not promise FSI, nonlinear multiphysics, or black-box co-simulation until
the workflow graph, data handoff, validation, and benchmark requirements are
explicit.

## Orchestration Position

P10 turns single-case workflows into directed graphs of local operations. Each
node remains a deterministic tool or solver action, and every edge records the
data handoff, assumptions, units, and approval state.

## Development Order

### 1. Workflow Graph Contract

Define the `WorkflowGraph` model for multi-step simulations.

Target behavior:

- Store nodes, dependencies, data handoffs, required approvals, retries, stop
  conditions, artifact inputs and outputs, provenance, and stale-state rules.
- Support serial execution before parallel execution.
- Reject cycles, missing inputs, ambiguous units, and undeclared producers.

Suggested implementation area:

- `packages/core/src/opennavier_core/workflow_graph.py`
- Tests in `tests/test_workflow_graph.py`

Acceptance signal:

- Tests cover graph validation, cycle rejection, dependency ordering,
  stale-artifact detection, approval gates, and deterministic output.

### 2. Staged Coupling Handoffs

Implement explicit data transfer between completed solver stages.

Target behavior:

- Transfer fields, loads, temperatures, pressures, or metrics only through
  declared artifacts.
- Record interpolation, projection, unit conversion, coordinate-system, and
  mesh-compatibility assumptions.
- Fail clearly when a handoff cannot be validated.

Suggested implementation area:

- Core handoff models.
- Adapter-specific export and import helpers.

Acceptance signal:

- Tests cover compatible handoffs, unit mismatch, mesh mismatch, missing
  source artifacts, interpolation metadata, and report limitations.

### 3. Weak Coupling Workflow Examples

Add first graph examples without claiming full co-simulation.

Target behavior:

- Support examples such as CFD pressure to structural load, thermal result to
  structural expansion, and mesh generation to multiple solver cases.
- Require human approval before consuming one solver result as another solver's
  load or boundary condition.
- Include validation gaps in reports.

Suggested implementation area:

- Example workflow manifests.
- Core workflow tests with fake adapters.

Acceptance signal:

- Tests prove graph execution order, artifact handoff, required approvals,
  failure handling, and evidence report generation.

### 4. Failure Recovery And Partial Results

Make long workflows understandable when one stage fails.

Target behavior:

- Mark downstream nodes skipped when dependencies fail.
- Preserve partial artifacts and diagnostics.
- Generate retry plans only within declared retry limits.
- Avoid deleting failed run evidence.

Suggested implementation area:

- Core workflow execution package.
- CLI or MCP wrappers after package behavior is tested.

Acceptance signal:

- Tests cover partial completion, failed dependencies, skipped nodes, retry
  limits, preserved logs, and summary output.

## P10 Completion Gate

P10 is complete only when:

- `WorkflowGraph` can represent and validate multi-step local simulations.
- Staged coupling handoffs preserve units, provenance, and assumptions.
- Weak coupling examples are explicitly scoped and approval-gated.
- Failed workflow stages preserve evidence and produce clear next actions.
- Focused tests and the full available suite pass.
