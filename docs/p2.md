# P2 Development Order

P2 adds model-assisted and interactive workflows on top of deterministic P0 and
P1 contracts. The model can help draft specs, questions, plans, and
explanations, but it must not bypass typed validation, approval checkpoints, or
deterministic writers.

Start P2 only after the no-LLM workflow is reliable.

## Desktop UI Position

P2 is where the desktop Studio experience becomes a usable end-to-end local
workflow. The target is not advanced CAD editing yet; it is a closed loop over
existing deterministic contracts:

1. Open or create a local workspace.
2. Enter an engineering request in the chat box or load a spec.
3. Review structured questions, spec, plan, commands, and approval points.
4. Initialize or select a case.
5. Run checks and explicit solver commands locally.
6. Watch run status and logs.
7. Inspect diagnostics, report links, and manifest artifacts.
8. Return to the request or plan with visible evidence for the next action.

The Studio UI should call stable CLI/MCP/package contracts. It should not
invoke model CLIs directly, mutate solver files directly, or create geometry
outside typed operation/spec artifacts.

## Development Order

### 1. LLM Intent Interface

Add an `ask` style flow that turns natural language into structured local
requests.

Target behavior:

- Accept a natural-language engineering request.
- Use the configured model runner through the P1 adapter contract.
- Return one of: draft `SimulationSpec`, clarifying questions, draft
  `CaseBuildSpec`, or draft plan request.
- Validate every model response through typed schemas.
- Record provenance in the session artifact.
- Reject direct dictionary edits or file mutation instructions from model text.
  A model may propose a one-off `CaseBuildSpec` only as typed data that must
  pass validation, dry-run, and explicit approval before any files are written.
  Similar examples in the prompt are guidance only, not selectable generators.

Suggested implementation area:

- `packages/core/src/opennavier_core/intent.py`
- Optional CLI command after package behavior is tested.

Acceptance signal:

- Tests use mocked model responses and verify schema validation,
  `CaseBuildSpec` validation handoff, rejection handling, provenance, and no
  direct dictionary writes.

### 2. Frontend Chat Request Bridge

Package Studio chat-box input into the same structured local request used by
the CLI and agent workflow.

Target behavior:

- Capture chat text, workspace context, selected provider, and local-only
  policy.
- Send requests through the backend contract, not directly to a model CLI.
- Display validation errors, clarifying questions, approval prompts, and
  structured next actions.
- Keep provider configuration explicit.

Suggested implementation area:

- `apps/studio/src`
- Backend command bridge only after the CLI/MCP request shape is stable.

Acceptance signal:

- Frontend or scaffold tests cover request payload shape, provider
  configuration, local-only defaults, failure states, and approval prompts.

### 3. Agent Iteration Policy

Allow bounded fix proposals and rerun plans when diagnostics fail.

Target behavior:

- Convert known diagnostic failures into proposed remediation steps.
- Require explicit approval before file changes or reruns.
- Track changed files and commands in the session artifact.
- Enforce rerun limits and stop conditions.
- Start with proposal-only behavior before automatic application.

Suggested implementation area:

- `packages/core/src/opennavier_core/iteration_policy.py`
- Tests in `tests/test_iteration_policy.py`

Acceptance signal:

- Tests cover fix proposals, required approval points, changed files, rerun
  limits, refusal conditions, and stop conditions.

### 4. ParaView Report Assets

Generate report-ready visual assets from existing cases through the ParaView
adapter.

Target behavior:

- Generate batch scripts for screenshots.
- Capture command logs.
- Use deterministic artifact names.
- Include optional screenshot references in reports.
- Keep real ParaView execution marked as integration-only.

Suggested implementation area:

- `packages/paraview`
- Report integration in `apps/cli/src/opennavier/cli/reporting.py` or core
  reporting if reporting moves there.

Acceptance signal:

- Adapter and report tests cover script generation, log paths, artifact naming,
  optional screenshot inclusion, and absent-screenshot behavior.

### 5. Desktop Studio Runtime Workflow

Connect Studio to local diagnostics, run logs, and report artifacts.

Target behavior:

- Show visible commands before execution.
- Show run status and log paths.
- Show diagnostics state from `diagnostics.json`.
- Link to generated reports and manifests.
- Preserve local-only messaging and approval checkpoints.

Suggested implementation area:

- `apps/studio/src`
- Runtime bridge through stable CLI/MCP/package contracts.

Acceptance signal:

- Frontend or scaffold tests cover visible commands, diagnostics states, report
  links, local-only defaults, and failure states.

## P2 Completion Gate

P2 is complete only when:

- Natural-language requests enter through typed schemas.
- Model output can produce specs, questions, `CaseBuildSpec` artifacts, or
  plans, but cannot mutate files directly.
- Studio chat uses the same local request contract as CLI/MCP workflows.
- Fix-and-rerun behavior is bounded and approval-gated.
- ParaView assets can be included in reports when available.
- Studio can show local run, diagnostics, and report state.
- Focused tests and the full available suite pass.
