# P4 Development Order

P4 turns the current planner capability checks into an explicit simulation OS
kernel. The goal is for OpenNavier to know, in structured data, which workflows
are executable, which are incomplete, which are experimental, and which are out
of scope.

Do not start multi-solver adapter expansion, community plugins, or model-authored
capabilities until the capability registry can gate execution deterministically.

## OS Kernel Position

P4 is the first post-Studio platform layer. It does not add new physics by
itself. It makes every current and future physics workflow declare its support
boundary before the planner, CLI, MCP tools, Studio, or an LLM can present that
workflow as runnable.

The registry is the source of truth for capability status. Prompt examples,
frontend labels, and model confidence must not override it.

## Development Order

### 1. Capability Manifest Schema

Define the `CapabilityManifest` contract for simulation workflows.

Target behavior:

- Store capability id, version, owner, readiness state, supported physics,
  geometry classes, mesh strategies, solvers, validators, benchmarks, artifacts,
  assumptions, limitations, and required approvals.
- Distinguish executable, experimental, draft, deprecated, and unsupported
  states.
- Require explicit unsupported declarations for common near-miss requests.
- Preserve deterministic JSON output for review and diffs.

Suggested implementation area:

- `packages/core/src/opennavier_core/capabilities.py`
- Tests in `tests/test_capabilities.py`

Acceptance signal:

- Tests cover schema validation, required fields, readiness transitions,
  unsupported declarations, deterministic serialization, and invalid manifests.

### 2. Capability Registry Loader

Load built-in and workspace-local manifests through a path-safe registry.

Target behavior:

- Load built-in manifests shipped with OpenNavier.
- Load workspace-local manifests only from declared registry paths.
- Reject manifests that reference files outside the workspace or package.
- Return typed records for missing dependencies, invalid versions, and
  conflicting capability ids.

Suggested implementation area:

- `packages/core/src/opennavier_core/capability_registry.py`
- Tests in `tests/test_capability_registry.py`

Acceptance signal:

- Tests cover built-in loading, workspace loading, path safety, duplicate ids,
  version conflicts, missing files, and stable ordering.

### 3. Planner Gating

Route all executable planning through registry-backed capability checks.

Target behavior:

- Match a validated `SimulationSpec` against declared capabilities.
- Return structured capability results for executable, incomplete,
  experimental, unsupported, and dependency-missing states.
- Require benchmark and validator references before marking a capability
  executable.
- Keep not-yet-executable states distinct from missing user inputs.

Suggested implementation area:

- Existing planner package in `packages/core`
- MCP and CLI surfaces only after package behavior is tested.

Acceptance signal:

- Tests cover supported cavity and duct cases, complete-but-not-executable
  requests, experimental capabilities that require approval, and unsupported
  physics or geometry classes.

### 4. Dependency And Runtime Checks

Make solver and tool availability visible before execution.

Target behavior:

- Declare required executables, optional tools, minimum versions, and licensing
  notes in each capability.
- Report missing dependencies without modifying the workspace.
- Record dependency-check output in diagnostics and reports.
- Avoid auto-installing solvers or tools.

Suggested implementation area:

- `packages/core/src/opennavier_core/dependencies.py`
- Thin adapter hooks in existing solver packages.

Acceptance signal:

- Tests use fake executables and captured command output to verify dependency
  detection, version parsing, missing-tool diagnostics, and no writes during
  checks.

## P4 Completion Gate

P4 is complete only when:

- `CapabilityManifest` is the typed contract for supported workflow claims.
- The registry can load built-in and workspace manifests safely.
- The planner cannot mark a request executable unless a registry capability
  supports it.
- Missing dependencies and unsupported requests produce structured diagnostics.
- Focused tests and the full available suite pass.
