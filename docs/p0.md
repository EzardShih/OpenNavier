# P0 Development Order

P0 is the foundation for safe local automation. These items define where
OpenNavier is allowed to work, how simulation intent becomes inspectable
artifacts, and how solver execution stays auditable.

Do not start P1 orchestration, model calls, frontend runtime workflows, or
automatic reruns until the P0 exit criteria are met.

## Current Status

As of 2026-05-07, P0 is complete in this branch.

- Agent session artifacts are typed, local-only by default, path-safe, and
  covered by focused tests.
- Simulation plan artifacts and schema-backed planner results exist for the
  validated cavity `CaseBuildSpec` baseline.
- Runner package APIs confine solver logs to the case path or explicit run
  directory.
- CLI `check`, `doctor`, `report`, `init cavity`, and `run` exist.
- `doctor` and `report` can write stable local-only diagnostics artifacts.
- Focused P0 tests, the full Python suite, and Ruff pass in the integration
  worktree.

## Desktop UI Position

P0 does not build the desktop UI runtime. It creates the contracts the desktop
UI must consume later: session artifacts, plan artifacts, path-safe run
artifacts, diagnostics JSON, and deterministic planner output.

The existing Studio scaffold may remain present, but P0 work should not add
chat execution, run buttons, result overlays, or Three.js editing workflows.
Those UI features depend on the P0 contracts being stable first.

## Development Order

### 1. Agent Session Model

Status: Complete as of 2026-05-07.

Create a typed local session artifact that acts as the durable audit trail for
future agent work.

Target behavior:

- Store engineering intent, validated spec references, plan references,
  command records, diagnostics, reports, generated artifacts, and provenance.
- Default to local-only behavior with no cloud upload fields enabled.
- Load and validate an existing session artifact deterministically.
- Reject artifact references that escape the workspace.
- Preserve enough provenance to explain which tool wrote or changed each
  artifact.

Suggested implementation area:

- `packages/core/src/opennavier_core/session.py`
- Tests in `tests/test_session_artifact.py`

Acceptance signal:

- Tests cover schema validation, path safety, malformed session loading,
  artifact references, no-cloud defaults, and deterministic JSON output.

Exit criteria:

- A session can be created, written, loaded, and validated without invoking
  OpenFOAM, MCP, Studio, or any model runner.

### 2. Simulation Plan Artifact

Add an explicit plan model that bridges planner-accepted `SimulationSpec`
instances, validated `CaseBuildSpec` artifacts, and deterministic tools.

OpenNavier's product ambition is broad physical simulation intake, but P0 plans
must only describe executable work backed by current deterministic capabilities.
Those capabilities should be schema-backed case-build operations and
MCP-callable validation/write tools. OpenNavier should not require reusable case
generators or an internal case-generation library.

Target behavior:

- Convert a validated, executable `SimulationSpec` into a serializable plan
  artifact.
- Capture assumptions, required tools, ordered commands, expected artifacts,
  `CaseBuildSpec` references, pre-flight checks, approval checkpoints, risks,
  and report outputs.
- Produce stable JSON ordering for repeatable diffs and tests.
- Keep incomplete or arbitrary physical-simulation intake out of the plan
  artifact. The P1 clarification loop owns missing information and broad
  capability discovery.
- Keep not-yet-executable request states out of `SimulationPlan`; those belong
  to the planner result, not the executable plan artifact.
- Do not require a built-in case-generator name. A plan may reference a
  validated local `CaseBuildSpec` artifact that describes how deterministic
  MCP/package tools will create and validate the solver case.

Suggested implementation area:

- `packages/core/src/opennavier_core/plan.py`
- Tests in `tests/test_simulation_plan.py`

Acceptance signal:

- Plan model tests cover accepted cavity plan shape, required executable plan
  fields, `CaseBuildSpec` references, approval points, and stable JSON output.
  Missing-input behavior is covered by the P1 clarification loop instead of
  this layer.

Exit criteria:

- A valid cavity `SimulationSpec` can produce a plan artifact without using an
  LLM or writing OpenFOAM dictionaries.
- No incomplete request can be promoted to an executable plan artifact by this
  layer.

### 3. Run Safety

Status: Complete as of 2026-05-07.

Harden solver execution boundaries before exposing runner APIs through the CLI
or agent workflows.

Target behavior:

- Refuse missing case paths without creating them.
- Refuse unsafe case paths when a workspace root is provided.
- Keep generated run artifacts under the case path or an explicit run directory.
- Reject caller-provided log paths that escape the allowed target.
- Preserve existing no-shell command behavior by accepting argument sequences,
  not command strings.

Suggested implementation area:

- `packages/openfoam/src/opennavier/openfoam/runner.py`
- Shared path helpers if the same behavior is needed by CLI and MCP.
- Tests in `tests/test_runner.py`

Acceptance signal:

- Path-safety tests prove solver logs and future run artifacts cannot be
  written outside the intended case or run directory.

Exit criteria:

- The runner cannot be used to write a log outside the allowed target, even
  when passed an absolute path or parent traversal.

### 4. CLI Run Workflow

Status: Complete as of 2026-05-07.

Wire explicit solver execution into the CLI after runner safety is complete.

Target behavior:

- `opennavier run <case_path>` executes an explicit solver command through the
  runner API.
- Support local execution first.
- Support Docker selection only through explicit options.
- Print the selected command, runner, return code, and log path.
- Return a nonzero CLI exit code for missing executables and nonzero solver
  returns.
- Write a visible solver log under the allowed case or run directory.

Suggested implementation area:

- `apps/cli/src/opennavier/cli/main.py`
- Tests in `tests/test_cli.py`

Acceptance signal:

- CLI tests cover success, command-not-found failure, nonzero return codes,
  selected runner, Docker selection, and log output.

Exit criteria:

- A user can run a deterministic command against a known case and inspect the
  exact command and log path afterward.

### 5. Diagnostics Artifact Output

Status: Complete as of 2026-05-07.

Make diagnostics available as a durable artifact, not only stdout.

Target behavior:

- `doctor` or `report` can write `diagnostics.json`.
- The artifact contains stable diagnostic records with status, code, message,
  path, and metadata.
- Include counts by status for quick consumers.
- Include local-only/no-cloud metadata.
- Keep stdout JSON and artifact JSON compatible but not coupled to formatting.

Suggested implementation area:

- `packages/core/src/opennavier_core/diagnostic_artifact.py`
- CLI option in `apps/cli/src/opennavier/cli/main.py`
- Tests in `tests/test_diagnostics_artifact.py` and `tests/test_cli.py`

Acceptance signal:

- JSON artifact tests cover schema, counts, diagnostic codes, paths,
  deterministic ordering, no-cloud flags, and overwrite behavior.

Exit criteria:

- CLI, MCP, Studio, and reports have one stable diagnostics artifact contract to
  consume.

### 6. Schema-Driven Planner Baseline

Add the first no-model planning rules after session and plan artifacts exist.

The planner is the capability gate, not the product boundary. It should grow
toward many simulation families, but it must only mark a request executable
when OpenNavier has deterministic rules for the selected physics, geometry,
mesh, solver, checks, and artifacts.

The long-term path is not a closed library of hardcoded or reusable case
generators. A future LLM should use prompt examples only as guidance, then
produce a one-off `CaseBuildSpec` through a typed schema. MCP tools then
validate, dry-run, write, check, and report the case. P0 should establish the
planner contract for that flow without invoking an LLM.

Target behavior:

- Map a supported spec plus a validated `CaseBuildSpec` to validation steps,
  run commands, expected logs, diagnostics, and report outputs.
- Define the minimum build/capability fields the planner needs: physics,
  geometry requirements, mesh strategy, solver family, dictionary/field writer
  operations, validators, expected artifacts, and required approvals.
- Start with cavity as a checked-in `CaseBuildSpec` fixture or equivalent
  deterministic capability proof, not as a reusable generation pattern.
- Add duct, pipe, or another family by expanding schema-validated build
  operations and matching validators, not by adding a built-in generator.
- Keep deterministic ordering for commands, checks, and artifacts.
- Return a typed planner result: either an executable `SimulationPlan` or a
  structured not-yet-executable capability result for a complete spec that has
  no current deterministic support.
- Reject build specs that depend on raw, unvalidated OpenFOAM dictionary text,
  unknown writer operations, missing validators, or paths outside the workspace.
- Do not own missing-input detection or broad simulation intake; incomplete and
  ambiguous requests are handled by the P1 clarification loop before planner
  entry.

Suggested implementation area:

- `packages/core/src/opennavier_core/case_build_spec.py`
- `packages/core/src/opennavier_core/planner.py`
- Planner result/rejection types may live here; `plan.py` should remain the
  executable plan artifact schema.
- Tests in `tests/test_planner.py`
- Build-spec schema tests in `tests/test_case_build_spec.py`

Acceptance signal:

- Tests cover cavity planning, first duct or pipe planning when available,
  build-spec schema validation, rejection of raw dictionary text,
  not-yet-executable physics, geometry, solver families, and deterministic
  ordering.

Exit criteria:

- A model or frontend can request a plan artifact instead of inventing solver
  commands or dictionary edits.
- A future LLM-generated `CaseBuildSpec` can be accepted only as typed data that
  passes deterministic validation and is then executed through MCP/package tool
  operations.

## P0 Completion Gate

P0 is complete only when all of the following are true:

- Session artifacts are typed, local-only by default, and path-safe.
- Plan artifacts are typed, deterministic, and generated from validated specs.
- Case-build specs are typed, path-safe, and validated before a planner can
  reference them.
- Runner writes are confined to the case or run directory.
- `opennavier run <case_path>` exists and is tested.
- `diagnostics.json` output exists and is tested.
- The baseline planner maps supported specs plus validated case-build specs to
  deterministic tools and rejects complete specs without current deterministic
  support using typed capability results.
- Focused tests and the full available suite pass.
