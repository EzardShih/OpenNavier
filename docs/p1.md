# P1 Development Order

P1 connects the P0 contracts into a deterministic engineering workflow. The
goal is a useful local OpenFOAM automation product before natural-language
planning, Studio runtime integration, or autonomous design loops are added.

Start P1 only after P0 session, plan, run, diagnostics, and planner contracts
are complete.

## Desktop UI Position

P1 still does not make Studio the main runtime surface. It prepares the
deterministic workflow that the desktop UI will call later: inspect, validate,
plan, initialize, check, run, diagnose, report, and summarize.

If Studio changes are needed in P1, keep them limited to contract readiness:
documenting payload shapes, adding static scaffold affordances, or proving that
the UI can consume stable CLI/MCP/package outputs. Avoid chat-driven execution
or interactive CAD editing in P1.

## Development Order

### 1. Agent Tool Loop

Build a no-LLM workflow that uses the deterministic package APIs in a stable
order.

Target behavior:

- Inspect a workspace.
- Validate or load a `SimulationSpec`.
- Create or load a plan artifact.
- Initialize a supported case.
- Run pre-flight checks.
- Execute the selected solver command when requested.
- Collect diagnostics.
- Write report and manifest artifacts.
- Summarize next actions from structured evidence.

Suggested implementation area:

- `packages/core/src/opennavier_core/workflow.py`
- Thin CLI or MCP entrypoint after package API tests exist.

Acceptance signal:

- Tests cover tool ordering, skipped steps, failure handling, artifact
  references, stable summaries, and no LLM dependency.

### 2. Clarifying Questions

Return concrete questions for incomplete or ambiguous simulation requests
instead of guessing.

Target behavior:

- Detect missing geometry, units, fluid properties, boundary conditions, solver
  family, mesh intent, objective, and output expectations.
- Return structured question records.
- Include the missing field, why it matters, and acceptable answer shape.
- Keep not-yet-executable case classes distinct from missing inputs.
- Add a deterministic clarification loop tool that can be called by a future
  LLM workflow, but does not depend on an LLM in P1.
- Accept the current request text, any partial `SimulationSpec`, accumulated
  user answers, and known planner/capability results.
- Return one of: more clarifying questions, complete-but-not-yet-executable,
  ready-to-plan, or stopped.
- Confirm readiness through `SimulationSpec` validation plus deterministic
  planner/capability acceptance, not through model confidence.
- Preserve stop conditions such as maximum question turns, user-declined
  required information, not-yet-executable capability, or explicit user
  cancellation.

Suggested tool shape:

- `clarification_update` receives the current intake state and a user answer.
- `clarification_status` returns structured state for CLI, MCP, Studio, or a
  future model tool call.
- The tool returns typed records only; it must not write solver files, execute
  commands, or mark a request runnable without planner and `CaseBuildSpec`
  acceptance.

Suggested implementation area:

- `packages/core/src/opennavier_core/questions.py`
- `packages/core/src/opennavier_core/clarification_loop.py`
- Tests in `tests/test_clarifying_questions.py`
- Loop tests in `tests/test_clarification_loop.py`

Acceptance signal:

- Tests cover missing geometry, fluid properties, boundary conditions,
  objective, units, not-yet-executable geometry, and not-yet-executable physics.
- Loop tests cover accumulated answers, repeated question turns, transition
  from incomplete to ready-to-plan, complete-but-not-yet-executable requests,
  stop conditions, and no LLM dependency.

### 3. Case-Build MCP Tools

Expose schema-backed case construction through MCP so a future LLM can produce
a one-off `CaseBuildSpec` from prompt examples instead of raw OpenFOAM files.

Target behavior:

- Validate a user- or LLM-proposed `CaseBuildSpec` against the core schema.
- Dry-run a build spec to return planned file operations, writer operations,
  validators, commands, expected artifacts, and approval points without writing.
- Write a case only through known case-build writer operations after path-safety,
  schema validation, dry-run, and explicit overwrite checks pass.
- Return typed capability results that distinguish schema errors, missing
  writers, missing validators, not-yet-executable physics, and path violations.
- Reject raw dictionary blobs, arbitrary file mutations, shell command strings,
  and paths outside the workspace.
- Treat prompt examples as non-executable guidance only. They must not be
  registered, selected, or reused as executable case patterns.

Suggested implementation area:

- `packages/core/src/opennavier_core/case_build_spec.py`
- `packages/openfoam/src/opennavier/openfoam/case_build_writer.py`
- `packages/mcp/src/opennavier/mcp/case_build_tools.py`
- Tests in `tests/test_case_build_spec.py`
- MCP tests in `tests/test_mcp_case_build_tools.py`

Acceptance signal:

- Tests cover build-spec validation, dry-run output, path safety, rejection of
  raw dictionary text, overwrite guards, typed capability results, and parity
  between MCP tools and package APIs.

### 4. Pipe Or Duct Build-Spec Coverage

Add the next executable schema-backed build-spec coverage after cavity.

Target behavior:

- Add either pipe-flow or duct-pressure-drop build-spec behavior.
- Generate a complete OpenFOAM case tree deterministically through case-build
  writer operations.
- Preserve overwrite guards.
- Add a committed example only after generated output is stable.
- Keep generated runtime artifacts out of source packages and examples.

Suggested implementation area:

- `packages/openfoam/src/opennavier/openfoam/case_build_writer.py`
- CLI or MCP entrypoint after package API tests exist.
- Example under `examples/pipe-flow` or `examples/duct-pressure-drop`

Acceptance signal:

- Build-spec tests compare generated files, overwrite behavior, validation
  results, and committed example parity.

### 5. Solver Compatibility Checks

Validate that selected solver families agree with dictionaries, fields, and
case-build assumptions.

Target behavior:

- Check solver family against case dictionaries.
- Check required fields for supported case-build specs.
- Check known incompatible solver/dictionary combinations.
- Keep compatibility validation separate from case-structure validation.

Suggested implementation area:

- `packages/openfoam/src/opennavier/openfoam/solver_compatibility.py`
- Tests in `tests/test_solver_compatibility.py`

Acceptance signal:

- Tests cover valid cavity and duct or pipe cases plus known invalid
  solver/dictionary combinations.

### 6. MCP Diagnostics Expansion

Expose broader diagnostics through MCP as thin wrappers over package APIs.

Target behavior:

- Add mesh-quality diagnostics.
- Add full case diagnostics.
- Add diagnostics artifact output after P0 artifact behavior exists.
- Add report generation tools only through existing report APIs.
- Keep all MCP paths scoped to explicit workspace roots.

Suggested implementation area:

- `packages/mcp/src/opennavier/mcp/diagnostics_tools.py`
- New MCP report tool module if needed.

Acceptance signal:

- MCP tests prove workspace scoping, output shape, path safety, and parity with
  package APIs.

### 7. Model Runner Adapter Contract

Define the model boundary without adding natural-language execution yet.

Target behavior:

- Add provider-neutral request and response models.
- Add mocked subprocess adapters for Claude CLI, Codex CLI, and Gemini CLI.
- Support explicit provider selection.
- Support configurable command templates.
- Parse model output only into typed response models.
- Reject text that attempts direct file mutation or raw OpenFOAM dictionary
  edits.

Suggested implementation area:

- `packages/core/src/opennavier_core/model_runner.py`
- Tests in `tests/test_model_runner.py`

Acceptance signal:

- Tests cover provider selection, command construction, missing CLI handling,
  response parsing, schema rejection, and no direct file mutation from model
  text.

## P1 Completion Gate

P1 is complete only when:

- The no-LLM workflow can inspect, validate, plan, initialize, check, run,
  diagnose, report, and summarize.
- Missing inputs produce structured clarifying questions, and the deterministic
  clarification loop can keep asking until the request is ready-to-plan,
  complete-but-not-yet-executable, stopped, or explicitly cancelled.
- MCP case-build validation, dry-run, and write tools are thin, path-safe
  wrappers over package APIs.
- A second schema-backed executable build-spec path exists.
- Solver compatibility checks exist for supported case-build specs.
- MCP diagnostics and report tools are thin, path-safe wrappers.
- Model runner adapters are contract-tested but do not drive execution yet.
- Focused tests and the full available suite pass.
