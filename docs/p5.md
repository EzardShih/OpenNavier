# P5 Development Order

P5 defines the shared simulation language that lets OpenNavier grow beyond
OpenFOAM without fragmenting into solver-specific request shapes. The goal is a
backward-compatible ontology for physics, fields, units, materials, geometry,
boundary conditions, objectives, assumptions, and result artifacts.

Do not add broad multi-solver workflows until the ontology can describe their
inputs and outputs without losing the P0 to P4 safety and capability gates.

## Ontology Position

P5 is not a new solver layer. It is the typed vocabulary that allows the
planner, capability registry, adapters, reports, and Studio to talk about the
same engineering intent across different tools.

The existing `SimulationSpec` remains the public entry point. P5 evolves it
through compatible schema additions and migrations rather than replacing it
with a parallel model.

## Development Order

### 1. Simulation Ontology Model

Create the `SimulationOntology` contract and mapping rules.

Target behavior:

- Define canonical units, dimensions, materials, fields, boundary condition
  families, geometry classes, mesh intents, solver families, objectives, and
  result artifact types.
- Preserve current OpenFOAM-focused spec behavior through migrations.
- Reject unknown physics or boundary concepts unless a versioned extension
  declares them.
- Record assumptions and idealizations as first-class fields.

Suggested implementation area:

- `packages/core/src/opennavier_core/ontology.py`
- Tests in `tests/test_simulation_ontology.py`

Acceptance signal:

- Tests cover unit normalization, unknown-field rejection, backward-compatible
  loading of current specs, extension declarations, and deterministic output.

### 2. Cross-Solver Field And Unit Semantics

Normalize the physical meaning of fields before adapter translation.

Target behavior:

- Represent pressure, velocity, temperature, displacement, stress, heat flux,
  force, and derived metrics with units and dimensions.
- Validate dimensional consistency for common inputs and outputs.
- Keep solver-specific names as adapter mappings, not ontology primitives.
- Report ambiguous user units through clarifying questions.

Suggested implementation area:

- Core ontology and validation packages.
- Existing clarification loop after package tests exist.

Acceptance signal:

- Tests cover dimensional checks, field aliases, unit conversions, missing
  units, and solver-specific name mapping without changing user intent.

### 3. Materials And Boundary Families

Define reusable material and boundary abstractions.

Target behavior:

- Represent fluids, solids, thermal materials, and simple property tables.
- Represent boundary families such as inlet, outlet, wall, symmetry, fixed
  support, load, temperature, heat flux, and interface.
- Require adapters to declare which ontology concepts they can translate.
- Keep unsupported boundary families capability-gated.

Suggested implementation area:

- `packages/core/src/opennavier_core/materials.py`
- Boundary models in core spec modules.

Acceptance signal:

- Tests cover required material properties, incompatible materials and physics,
  boundary-family validation, and unsupported adapter mappings.

### 4. Result Artifact Ontology

Make outputs comparable across solvers and workflows.

Target behavior:

- Define artifact types for logs, meshes, fields, screenshots, plots, reports,
  metrics, convergence studies, and benchmark evidence.
- Include units, source command, producer, time step or load step, and field
  identity.
- Make reports consume ontology-backed artifact metadata.

Suggested implementation area:

- Core artifact and manifest modules.
- Report integration after artifact tests exist.

Acceptance signal:

- Tests cover artifact metadata validation, missing provenance, unit labels,
  report references, and stable manifest output.

## P5 Completion Gate

P5 is complete only when:

- Current `SimulationSpec` data can migrate into the ontology-backed model.
- Cross-solver fields, units, materials, boundaries, objectives, and artifacts
  have typed representations.
- Adapters and capabilities can declare ontology concepts they support.
- Unsupported ontology concepts remain non-executable until a capability covers
  them.
- Focused tests and the full available suite pass.
