# P9 Development Order

P9 expands geometry, meshing, and model preparation into an explicit platform
layer. The goal is to make geometry preparation reproducible and inspectable
before arbitrary CAD cleanup is attempted.

Do not let Studio, agents, or plugins mutate geometry or mesh artifacts outside
typed operations, declared adapters, and capability-specific validation.

## Model Preparation Position

P9 sits between engineering intent and solver input. It turns geometry,
boundary names, mesh strategy, simplification choices, and repair operations
into visible artifacts that can be reviewed before a solver run.

## Development Order

### 1. Geometry Operation Model

Define typed geometry operations for parametric and imported models.

Target behavior:

- Represent create, import, scale, translate, tag, simplify, split, merge,
  suppress feature, and export operations with inputs, outputs, units, and
  provenance.
- Keep the operation list as the durable source of truth for Studio geometry
  edits.
- Reject operations that are unsupported by the selected capability or adapter.

Suggested implementation area:

- `packages/core/src/opennavier_core/geometry_ops.py`
- Studio backend bridge after core tests exist.

Acceptance signal:

- Tests cover operation schema validation, unit handling, path safety,
  unsupported operations, deterministic serialization, and undo metadata.

### 2. Boundary Tagging And Semantic Surfaces

Make boundary identity explicit before meshing and solver writing.

Target behavior:

- Store semantic tags for inlet, outlet, wall, symmetry, load, support,
  interface, heat-transfer, and measurement regions.
- Validate that required tags exist before case writing.
- Preserve mappings from CAD faces to mesh patches and solver boundaries.

Suggested implementation area:

- Core geometry and mesh metadata modules.
- Gmsh and FreeCAD adapter integration after package tests exist.

Acceptance signal:

- Tests cover required tags, duplicate tags, missing mappings, stale geometry,
  mesh patch mapping, and report visibility.

### 3. Mesh Strategy And Failure Diagnosis

Represent mesh intent as structured data instead of tool-specific commands.

Target behavior:

- Store element type, target size, refinement regions, boundary-layer intent,
  quality thresholds, and adapter preferences.
- Diagnose common mesh failures from logs and produced meshes.
- Propose remeshing changes as bounded recommendations requiring approval.

Suggested implementation area:

- Core mesh strategy module.
- Gmsh adapter diagnostics.

Acceptance signal:

- Tests cover mesh-strategy validation, invalid thresholds, diagnostic parsing,
  bounded remesh proposals, and no automatic rerun without approval.

### 4. CAD Import And Simplification Gate

Add a cautious path for imported geometry.

Target behavior:

- Import CAD files only into declared workspace artifact paths.
- Inspect units, bodies, open shells, small features, nonmanifold conditions,
  and missing boundary tags.
- Keep arbitrary industrial CAD cleanup marked experimental until benchmarks
  and adapter support prove reliability.

Suggested implementation area:

- FreeCAD adapter and core geometry inspection APIs.
- Integration tests only when external tools are available.

Acceptance signal:

- Tests use small fixtures or fake adapter output to verify import metadata,
  failure diagnostics, simplification proposals, and capability gating.

## P9 Completion Gate

P9 is complete only when:

- Geometry operations, boundary tags, mesh strategies, and model-prep artifacts
  are typed and reproducible.
- Mesh failures can produce structured diagnostics and bounded remesh proposals.
- Imported CAD remains gated by declared capabilities and visible limitations.
- Studio geometry edits serialize through backend contracts.
- Focused tests and the full available suite pass.
