# P8 Development Order

P8 builds the verification, benchmark, and evidence corpus that lets
OpenNavier decide whether a capability is trustworthy enough to execute. The
goal is to turn engineering validation into first-class local artifacts.

Do not promote experimental or draft capabilities to executable status without
benchmark manifests and repeatable evidence checks.

## Verification Position

P8 is the trust layer of the simulation OS. It does not replace professional
validation, but it forces every supported workflow to show what was checked,
which benchmark or analytical rule applies, and where the remaining risk lives.

## Development Order

### 1. Benchmark Manifest Schema

Define the `BenchmarkManifest` contract for capability evidence.

Target behavior:

- Store benchmark id, capability id, physics, geometry, solver adapter,
  fixture paths, analytical checks, expected metrics, tolerances, required
  artifacts, and evidence report links.
- Distinguish unit benchmarks, golden cases, integration benchmarks,
  convergence studies, and user-supplied validation cases.
- Require benchmark references before a capability reaches executable status.

Suggested implementation area:

- `packages/core/src/opennavier_core/benchmarks.py`
- Tests in `tests/test_benchmarks.py`

Acceptance signal:

- Tests cover schema validation, missing fixtures, tolerance validation,
  capability linkage, deterministic output, and invalid benchmark states.

### 2. Analytical Sanity Checks

Add small physics checks that catch plausible but wrong simulations.

Target behavior:

- Support dimensional checks, conservation checks, hydrostatic pressure checks,
  simple beam or plate formulas, thermal resistance checks, and known CFD
  pressure-drop ranges when the capability declares them.
- Report sanity-check failures separately from solver failures.
- Include assumptions and applicability limits in reports.

Suggested implementation area:

- `packages/core/src/opennavier_core/sanity_checks.py`
- Domain-specific checks in adapter or capability packages.

Acceptance signal:

- Tests cover passing checks, failing checks, missing required inputs,
  tolerance handling, and report inclusion.

### 3. Evidence Report Artifacts

Generate durable evidence for benchmark and production runs.

Target behavior:

- Record inputs, commands, solver versions, logs, metrics, plots, screenshots,
  benchmark comparison, convergence information, and validation gaps.
- Keep evidence local and path-safe.
- Allow reports to state that a workflow is unvalidated when evidence is
  incomplete.

Suggested implementation area:

- Core reporting and manifest modules.
- CLI and MCP report surfaces after package tests exist.

Acceptance signal:

- Tests cover evidence report metadata, missing evidence warnings, benchmark
  comparison tables, stale artifacts, and stable report output.

### 4. Capability Promotion Gate

Make benchmark evidence part of readiness transitions.

Target behavior:

- Prevent draft or experimental capabilities from becoming executable unless
  required benchmarks pass.
- Store promotion history and reviewer notes.
- Preserve failed benchmark records instead of deleting them.

Suggested implementation area:

- Capability registry readiness logic.
- Tests shared with P4 capability models.

Acceptance signal:

- Tests cover promotion success, promotion failure, missing benchmark evidence,
  failed evidence retention, and reviewer metadata.

## P8 Completion Gate

P8 is complete only when:

- `BenchmarkManifest` is the typed contract for capability evidence.
- Analytical sanity checks can run and report structured results.
- Evidence reports can reference benchmarks, metrics, logs, and validation gaps.
- Capability promotion requires benchmark evidence.
- Focused tests and the full available suite pass.
