# P11 Development Order

P11 turns OpenNavier into an open-source platform by defining plugins,
certification, sandboxing, and trust states. The goal is to let the community
add capabilities without weakening local-first safety or engineering evidence.

Do not load third-party solver capabilities as executable until plugin metadata,
permissions, tests, benchmarks, and certification state are validated.

## Ecosystem Position

P11 is the boundary between the core OS and external contributions. A plugin
can contribute adapters, capabilities, validators, benchmarks, examples,
reports, and Studio extensions, but it cannot bypass the registry, ontology,
workflow, or evidence gates.

## Development Order

### 1. Plugin Manifest Contract

Define the `PluginManifest` format.

Target behavior:

- Store plugin id, version, owner, license, contributed capabilities, required
  permissions, adapter dependencies, tests, benchmark evidence, supported OSes,
  and certification status.
- Declare all file-system, process, network, and external executable needs.
- Reject plugins with unknown permissions or missing capability references.

Suggested implementation area:

- `packages/core/src/opennavier_core/plugins.py`
- Tests in `tests/test_plugin_manifest.py`

Acceptance signal:

- Tests cover manifest validation, permission declarations, missing capability
  links, version conflicts, invalid licenses, and deterministic output.

### 2. Plugin Loading And Sandbox Policy

Load plugins without giving them implicit trust.

Target behavior:

- Load local plugins from approved paths only.
- Default to no network access, no writes outside declared workspaces, and no
  hidden solver commands.
- Separate installed, enabled, trusted, certified, and blocked states.
- Surface plugin provenance in reports and manifests.

Suggested implementation area:

- Core plugin registry package.
- MCP or CLI plugin inspection tools after package tests exist.

Acceptance signal:

- Tests cover approved-path loading, blocked paths, trust-state transitions,
  permission denials, provenance, and disabled plugin behavior.

### 3. Certification Checks

Define the minimum evidence for a plugin capability to be trusted.

Target behavior:

- Require schema tests, fake-executable tests, benchmark manifests, evidence
  reports, licensing notes, and security review metadata.
- Preserve separate certification levels for experimental, verified, and
  certified capabilities.
- Keep certification local and reproducible before any marketplace concept.

Suggested implementation area:

- Core certification models.
- Documentation under contributor guides.

Acceptance signal:

- Tests cover certification success, missing tests, missing benchmarks, failed
  evidence, expired review state, and clear user-facing diagnostics.

### 4. Contributor Workflow

Document how open-source contributors add a new capability.

Target behavior:

- Require an issue or proposal, capability manifest, ontology mappings, adapter
  hooks, validators, benchmarks, example case, documentation, and review notes.
- Require TDD and focused validation commands.
- Reject contributions that allow LLM direct solver-file mutation or hidden
  execution paths.

Suggested implementation area:

- `docs/contributing-capabilities.md`
- Updates to repository contribution docs when they exist.

Acceptance signal:

- Documentation gives a complete contribution checklist and references the
  P4-P12 trust gates.

## P11 Completion Gate

P11 is complete only when:

- `PluginManifest` is the typed contract for extension packages.
- Plugin loading is path-safe and permission-aware.
- Certification states require tests, benchmarks, evidence, and review metadata.
- Contributor docs explain how to add capabilities without bypassing trust
  boundaries.
- Focused tests and the full available suite pass.
